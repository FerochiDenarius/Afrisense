================================================================================
1. SYSTEM OVERVIEW
================================================================================

AfriSense is a PHP/MySQL food services system that supports guest ordering, customer accounts, admin management, bookings, enquiries, reviews, delivery assignment, notifications, configurable web settings, and live support conversations.

The application is split into these main areas:
- backend/: reusable API-style controllers, models, helpers, middleware, database bootstrap, and routes.
- frontend/auth/: login, registration, email verification, password reset, role redirects, email sending, and shared auth helpers.
- frontend/includes/: public settings, theme variables, support helpers, remarks helpers, and shared public business rules.
- frontend/admin/: admin dashboard and management pages for orders, bookings, delivery, foods, users, roles, permissions, support, reports, settings, gallery, enquiries, and remarks.
- frontend/customer/: logged-in customer pages for ordering, payment, cart, bookings, enquiries, remarks, notifications, profile, settings, and support.
- frontend/landing/: public guest pages for homepage, menu, cart, checkout, order, payment, booking, support, gallery, remarks, services, enquiries, and contact.
- frontend/layouts and frontend/components/: reusable page shells, sidebars, headers, footer, navbar, alerts, modals, and loaders.
- frontend/assets/js/: client-side behavior such as support polling, form validation, cart animation, fullscreen controls, modal behavior, scroll restoration, and settings UI helpers.

2. MAIN REQUEST LIFECYCLE
================================================================================

Most PHP pages follow this sequence:
1. Page metadata is set, such as title, active menu item, CSS files, and script files.
2. Required shared helpers are loaded with require_once.
3. The user role is checked, for example afrisense_require_admin() or afrisense_require_customer().
4. Helper functions are declared for page-specific formatting, query generation, image lookup, or status mapping.
5. Request values are read from GET or POST and normalized.
6. POST actions are handled before the page renders.
7. Database queries load the records, metrics, counts, and detail panels needed for the page.
8. Data is rendered into HTML using htmlspecialchars to reduce XSS risk.
9. A shared layout file is required, or the page renders its own full HTML shell if it is standalone.

The repeated "Guard this block" comments mean the block only runs when a required condition is true, such as a valid status, a valid user id, a non-empty search term, or a valid POST action.

The repeated "Iterate through the data needed for this block" comments mean the code loops through an array of records, options, uploaded files, filters, settings, or database rows and applies the same logic to each item.

22. CROSS-CUTTING DATA FLOW SUMMARY
================================================================================

Guest order flow:
Guest selects food -> cart is stored in session -> checkout/order validates guest details -> customer row is found or created -> order rows are inserted -> admins are notified -> customer email is sent when enabled -> cash orders stop at confirmation while online methods show payment steps.

Customer order flow:
Customer logs in -> cart is stored in customer session -> customer row is linked to user -> orders are inserted -> admins and customer are notified -> customer sees orders in My Orders.

Booking flow:
Guest/customer submits booking -> customer row is found or created -> booking is inserted as Pending -> admins receive notification -> admin changes status -> customer receives notification.

Delivery flow:
Admin opens delivery management -> order is selected -> rider is assigned -> delivery assignment is inserted/updated -> order status follows delivery status -> customer/rider notifications are created.

Support flow:
Guest/customer opens support -> conversation is created or loaded -> default agent is assigned -> messages and attachments are saved -> live endpoint polls for changes -> sender and receiver see image/video/file previews.

Settings/theme flow:
Admin changes Web Settings -> settings controller validates and saves colors/settings -> public_settings loads saved values -> theme helper prints CSS variables -> layouts and standalone pages apply updated colors.

Notification flow:
Business event happens -> helper inserts notification rows for admins/customers/riders -> notification pages count unread rows -> open/read/delete actions update notification state.

Email flow:
Event requests email -> database SMTP settings are loaded -> SMTP message is built -> SMTP connection sends email -> failures return a structured result and should not crash order/booking pages.

23. IMPORTANT TABLE RELATIONSHIPS
================================================================================

roles -> users: each user has one role.

roles -> role_permissions -> permissions: roles receive permission access through role_permissions.

customers -> orders: orders belong to customers.

foods -> orders: each order row references a food item.

customers -> bookings: bookings belong to customers.

services -> bookings: bookings reference a service/package.

customers -> enquiries: enquiries are attached to customer contact records.

customers -> remarks: remarks/reviews are attached to customers when possible.

orders -> delivery_assignments: delivery assignments connect riders to orders.

users -> delivery_assignments: delivery rider users are assigned to deliveries.

users -> notifications: notifications target users.

users -> audit_logs: user actions may create audit log records.

support_conversations -> support_messages -> support_attachments: support conversations contain messages and optional attachments.
