================================================================================
1. INTRODUCTION
================================================================================

AfriSense Food Services is a web-based food service management system developed to support online food ordering, catering service booking, customer enquiries, customer reviews, delivery assignment, notifications, live support, and administrative business control. The system supports both guest users and registered customers, while administrators manage the operational side of the platform from a secured admin dashboard.

The application is built with PHP, MySQL, HTML, CSS, and JavaScript. It is designed to run in a XAMPP environment and includes first-run database setup support so the database can be created automatically when the project is copied to another machine and opened.

The system separates public, customer, and administrator workflows. Public users can browse menus, place guest orders, book services, submit enquiries, and chat with support. Registered customers can manage orders, bookings, enquiries, support conversations, notifications, and account settings. Administrators can manage orders, bookings, foods, services, customers, users, roles, permissions, delivery, reports, settings, notifications, enquiries, remarks, gallery content, and support conversations.

================================================================================
2. PROBLEM STATEMENT
================================================================================

Many food service businesses still manage orders, bookings, customer complaints, delivery assignments, and notifications through manual methods such as phone calls, paper records, WhatsApp messages, or disconnected spreadsheets. These methods can cause lost orders, delayed responses, poor delivery tracking, difficulty confirming customer payments, weak record keeping, and limited visibility into business performance.

AfriSense addresses this problem by providing one integrated system where customers and guests can place orders or bookings online, while administrators can manage the entire workflow from one dashboard. The system improves accuracy, speed, traceability, customer communication, and reporting.

Main Objective:
To develop a complete food services web application that allows AfriSense to manage customer orders, bookings, support, delivery, and business administration from one centralized platform.

10. To provide role-based access control through roles and permissions.

6. BUSINESS RULES
================================================================================

Authentication and Access Rules:
1. Only authenticated users can access customer and admin dashboards.
2. Customer accounts are redirected to customer pages.
3. Admin/staff accounts are redirected to admin pages.
4. Admin pages require an administrator or staff-type account.
5. Roles and permissions determine which admin functions a staff user may access.
6. Email verification is required for account verification workflows.

Ordering Rules:
1. Guests can place orders only when guest checkout is enabled in settings.
2. Ordering is blocked when delivery/order settings make ordering unavailable.
3. A cart must contain at least one food item before checkout.
4. A valid customer name, email, phone number, delivery address, and payment method are required for guest orders.
5. Logged-in customer orders are linked to the customer user account.
6. Each food item in the cart creates an order row, allowing item-level tracking.
7. Delivery fee is calculated from configured delivery settings, subtotal, and optional zone/address rules.
8. Free delivery applies when subtotal reaches the configured free-delivery threshold.
9. Cash on Delivery orders do not require online payment before moving to the next phase.
10. Online payment methods such as Mobile Money, Card Payment, Bank Transfer, or configured gateways require the user to proceed through the payment flow.
11. Paid/online orders can be auto-confirmed when the setting is enabled.
12. Admin order status updates notify the customer through in-app notification and email when enabled.

Payment Rules:
1. Only payment methods enabled in settings are shown to customers.
2. Disabled payment methods cannot be submitted successfully.
3. Cash on Delivery is treated differently from online payment methods.
4. Payment instructions are loaded from system settings.
5. Payment status can be updated by admin actions.
6. Email notification failures should not crash order placement.

Booking Rules:
1. Bookings require customer contact details, a selected service, event date/time, guest count, and location.
2. New bookings are created with Pending status.
3. Admins can update booking status to Pending, Confirmed, Completed, or Cancelled.
4. Booking status updates notify the linked customer account when one exists.
5. Cancelled bookings are excluded from booking revenue totals.

Delivery Rules:
1. Delivery assignment is connected to an order.
2. Only users with delivery rider role should be assigned as riders.
3. Delivery status can update the related order status.
4. Payment-on-delivery amount and change can be recorded.
5. Customers and riders can receive notifications about delivery updates.
6. Delivery management uses assignment status when available and falls back to order status otherwise.

Support Rules:
1. Guests can open support conversations using a session guest token.
2. Logged-in customers use their account identity for support conversations.
3. Admin is the default support agent when no agent has been created.
4. Support agent roles can handle support conversations.
5. A message must contain text or an attachment before it is saved.
6. Attachments are validated and stored with support messages.
7. Image and video attachments show previews for sender and receiver.
8. Support chat uses live polling so users do not need to refresh manually.
9. Sent and received message sounds are supported.

Notification Rules:
1. Important actions create notifications for users, admins, customers, or riders.
2. Notifications can be marked as read, opened, deleted, or marked all as read.
3. Notification action URLs must be internal/safe before redirecting.
4. Notification counters show unread activity in admin and customer interfaces.

Settings Rules:
1. Website settings control branding, colors, company information, social links, delivery settings, payment settings, SMTP settings, and maintenance mode.
2. Theme colors are saved in the database and printed as CSS variables.
3. Only valid hex color values are accepted for configurable colors.
4. SMTP settings control email delivery.
5. Maintenance mode can block public pages.
6. Items per page controls pagination size in admin tables.
7. Settings migration logic adds missing columns without destroying existing data.

Security Rules:
1. SQL queries use prepared statements for user input.
2. Output is escaped with htmlspecialchars in page rendering.
3. Passwords are hashed before storage.
4. Reset and verification tokens are stored and validated.
5. Uploads are validated before being moved into public upload folders.
6. Role checks protect admin pages.

8. SYSTEM WORKFLOWS
================================================================================

8.1 Guest Order Workflow
1. Guest opens public order/menu page.
2. Guest selects foods and adds them to session cart.
3. Guest enters name, email, phone, delivery address, and payment method.
4. System validates cart and customer details.
5. System finds or creates a customer record.
6. System calculates subtotal, delivery fee, and total.
7. System inserts one order row for each cart item.
8. System creates admin notifications.
9. System sends customer email when email notifications are enabled.
10. If Cash on Delivery is selected, the user is taken to order confirmation.
11. If an online payment method is selected, the user proceeds through the payment flow.

8.2 Registered Customer Order Workflow
1. Customer logs in.
2. Customer opens customer order page.
3. Customer adds foods to cart.
4. Customer provides delivery/payment details.
5. System links order to the logged-in customer.
6. System creates order rows.
7. System notifies admins and customer.
8. Customer can view the order in My Orders.

8.3 Booking Workflow
1. Guest or customer opens booking page.
2. User selects service/package and enters event details.
3. System validates contact, service, date, time, guest count, and location.
4. System finds or creates a customer record.
5. System inserts booking with Pending status.
6. System notifies administrators.
7. Admin reviews the booking.
8. Admin updates status to Confirmed, Completed, or Cancelled.
9. System notifies the linked customer account when available.

8.4 Admin Order Management Workflow
1. Admin opens Orders page.
2. System loads order metrics, filters, paginated orders, and selected order details.
3. Admin searches, filters, views, or scrolls the order list.
4. Admin changes order status or payment status.
5. System updates the order record.
6. System creates customer notification.
7. System sends customer email if enabled.

8.5 Delivery Management Workflow
1. Admin opens Delivery Management page.
2. System loads orders with customer, payment, rider, and delivery assignment data.
3. Admin selects/clicks an order.
4. Admin assigns a delivery rider.
5. System creates or updates delivery assignment.
6. Admin updates delivery status.
7. System updates order status according to delivery status.
8. System notifies customer and rider.

8.6 Support Chat Workflow
1. Guest or customer opens support page.
2. System loads existing conversation or creates a new one.
3. System assigns default admin/agent.
4. User sends text, emoji, image, video, or file attachment.
5. System stores message and attachment.
6. Agent receives conversation in admin support page.
7. JavaScript polling fetches new messages automatically.
8. Notification sounds play for sent and received messages.

8.7 Settings Workflow
1. Admin opens Web Settings.
2. Admin changes branding, theme colors, delivery, payment, email, social, or maintenance values.
3. System validates and saves settings.
4. Theme helper prints saved colors as CSS variables.
5. Public, customer, and admin pages reflect new settings.

9. SYSTEM ARCHITECTURE
================================================================================

Architecture Style:
The system uses a PHP server-rendered architecture with reusable helpers, page controllers, backend models/controllers, MySQL database, and JavaScript enhancements.

Layers:
1. Presentation Layer:
   - HTML/PHP pages in frontend/admin, frontend/customer, and frontend/landing.
   - CSS files in frontend/assets/css.
   - JavaScript files in frontend/assets/js.

2. Application Logic Layer:
   - frontend/auth/auth_bootstrap.php
   - frontend/includes/public_settings.php
   - frontend/includes/support_helpers.php
   - frontend/includes/remarks_helpers.php
   - frontend/admin page logic
   - frontend/customer page logic
   - frontend/landing page logic

3. Backend/API Layer:
   - backend/controllers
   - backend/models
   - backend/routes
   - backend/middleware
   - backend/helpers

4. Data Layer:
   - MySQL database afrisense_db
   - sql/afrisense_db_schema.sql
   - backend/config/database.php

5. External Services:
   - SMTP email server
   - Browser File Upload API
   - Browser Fullscreen API
   - XAMPP Apache/MySQL runtime

Architecture Notes:
- Most user-facing pages are server-rendered PHP pages.
- JavaScript improves interactivity but core workflows still submit to PHP.
- Database settings control key behavior such as payments, delivery, theme colors, SMTP, and maintenance mode.
- The database bootstrap supports first-run installation in XAMPP.

14. KEY MODULE EXPLANATION
================================================================================

Authentication Module:
The authentication module manages login, logout, session user retrieval, role detection, customer registration, email verification, password reset, and role-based redirects.

Ordering Module:
The ordering module manages food browsing, cart storage, delivery fee calculation, guest/customer order validation, order insertion, payment method handling, notifications, and customer email updates.

Booking Module:
The booking module manages service selection, event details, booking submission, admin approval, booking status tracking, and customer notification.

Delivery Module:
The delivery module manages assigning riders to orders, updating delivery statuses, collecting Cash on Delivery amounts, synchronizing delivery and order statuses, and notifying customers/riders.

Support Module:
The support module manages guest/customer conversations, default agent assignment, message storage, attachments, image/video previews, polling, and message sounds.

Settings Module:
The settings module lets admins configure website identity, colors, company details, payment methods, delivery rules, email SMTP, social links, maintenance mode, and pagination settings.

Notification Module:
The notification module records system events for users and allows viewing, opening, marking read, marking all read, and deleting notifications.

Roles and Permissions Module:
The roles and permissions module controls access by connecting users to roles and roles to permissions.

Reports Module:
The reports module summarizes revenue, orders, bookings, customers, food performance, payment methods, and recent report activity.
